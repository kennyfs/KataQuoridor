## 3. Root causes of the parity failures

The intermediate commit had no working parity test (§1.3 #3), so there was no failure to bisect, only the claim that
the test "never passed". The systematic route of the prompt was followed instead (one position, symmetry 0, Eigen
FP32 against PyTorch, in the order inputs → value → misc → policy channels → trajectory, then the larger nets,
CUDA, symmetries). To find out whether the intermediate commit itself was wrong, the same one-position comparison
was run on a build of `8ae317b5` (value logits, misc, trajectory and both policy variants, `b1c32_q4`, start
position): Eigen and PyTorch agreed to 1.2e-6, so the exporter, `PolicyHeadDesc` / `ValueHeadDesc` reading, the
variant-major channel layout and the Eigen output copy were right. Only that one net and that one position were
checked on the old build.

### 3.1 CUDA: Scale8 not undone (the only C++ parity bug)

- **Symptom.** `b1c32_q4` at the start position: PyTorch and Eigen agree, CUDA (FP32 and FP16) differs by O(1)
  (value 1.85, policy 2.1). The difference was the same in FP32 and FP16, and the same for NCHW and NHWC layouts, so
  it was structural, not numeric. The Duel nets passed parity on the same CUDA binary (policy 3.5e-7).
- **Layer search.** With the backend's `DEBUG_INTERMEDIATE_VALUES` dumps against PyTorch's `extra_outputs`: input
  rows identical; the output of the first convolution was exactly 1/8 of PyTorch's (rms 0.0500 vs 0.4004); the
  policy output was 1/8 (rms 0.1656 vs 1.325).
- **Root cause.** The GPU backends call `ModelDesc::applyScale8ToReduceActivations()`, which runs the net with all
  activations scaled by 1/8 and sets `postProcessParams.outputScaleMultiplier = 8`. For Duel, `NNEvaluator::evaluate`
  multiplies the logits by that multiplier in its post-processing. The Q4 raw path skips all Duel post-processing, so
  nobody multiplied.
- **Fix.** `NNEvaluator::serve` multiplies every raw Q4 output (policy, value, misc, trajectory) by
  `outputScaleMultiplier` before the result is cached (`nneval.cpp`, hunk in §5). Eigen is unaffected (multiplier 1).

### 3.2 CUDA "FP32" is TF32 in NHWC

After 3.1, the CUDA FP32 comparison showed errors up to 1.2e-3 on policy logits for `b1c32_q4` in NHWC mode, but
1.7e-6 in NCHW mode. With `NVIDIA_TF32_OVERRIDE=0` the NHWC FP32 error is 1.5e-6, so the 1e-3 is TF32 (cuDNN's FP32 NHWC convolutions on
Ampere). This is not a code bug; the CUDA FP32 test runs with `NVIDIA_TF32_OVERRIDE=0` and NHWC (the Duel parity test
notes that CUDA NCHW rejects transformer nets), and the CUDA FP16 test is the realistic precision measurement.

### 3.3 Not bugs, but checked explicitly

- Export order and shapes of the Q4 policy head (`conv2p`, the `linear_pass*` dummies) and value head (`v3`,
  `sv3`, ownership conv): correct (parity at 1e-6 for the 6 policy channels separately, so the variant-major layout
  `channel = variant · 3 + plane` is right in PyTorch, in the exported `conv2p` and in the backend copy).
- Activations and pooling: policy-head and value-head pooling differ in KataGo (`KataGPool` vs
  `KataValueHeadGPool`); `Q4PolicyHead` / `Q4ValueHead` use the right ones and parity holds on the 11 × 11 board.
- Input layout: `inputsUseNHWC` handled by `Q4NN::fillRow` / `applyInputSymmetry` for both layouts; tested in C++
  (NHWC and NCHW give the same symmetric rows). On CUDA the layouts were compared in the one-position debugging runs
  (NCHW with `cudaInputsUseNHWC = false`, NHWC, FP32 and FP16: the intermediate dumps agree); the T17 runs use NHWC.
- Post-processing: Q4 misc values are not multiplied by any Duel header multiplier on either side.

## 6. Design decisions and deviations from the plan

- **Plan §7.4 preferred design was implemented** (raw entry point in `NNEvaluator`, raw output block, backend change
  only where the counts must be accepted). The raw block is a `shared_ptr` member rather than a raw pointer
  (§1.3 #11).
- **Symmetry is applied by `Q4NN`**, the backend always gets 0; the cache key contains the symmetry because the cache
  stores the raw output at the transformed input.
- **The `outputScaleMultiplier` is applied in the server thread**, before caching, not by the caller (§3.1).
- **The head layouts are variant-major** (`channel = variant · 3 + plane`), the same convention as Duel's.
- **No averaging over symmetries in `NNEvaluator`** (Duel has `averageMultipleSymmetries`); the Q4 average is done
  in game space on decoded outputs (`q4tool symavg` shows it).
- **T18 repetition-state scenario** uses a hand-made history (a shuffled game with its ply counter reset), because
  a position with equal board, ply count and rules but a different repetition state practically does not occur in
  played games; the equivalence "same inputs ⇔ same key" is additionally checked on 2,500 sampled positions in C++.
- **`q4qtp nnpolicy` uses symmetry 0** (a fixed symmetry makes the move reproducible; random symmetries are a
  round-3 question).

## 9. Open questions for round 3 (search)

The plan (§8) says the value is a 5-vector and the search is max^n; the questions below are what the I/O leaves open.
They were checked against Plan §7–§8 and `Q4IO.md`; none is answered there.

1. **Which symmetry per evaluation?** The cache key contains the symmetry, so a random symmetry per evaluation means
   an expected cache hit rate of about 1/8 for transpositions. Options: a symmetry derived from the position hash
   (stable per position, the cache works, the average over positions is still symmetric), random per evaluation
   (Plan §7.1 says "random symmetry per evaluation"), or averaging a few. This needs a decision before the search
   uses the cache.
2. **Draw value and value vector.** `Q4NN::Eval::valueAbs` is `[seat 0..3, draw]`. Does the search back up the 4 seat
   probabilities, or the expected score with the draw split equally between the alive seats (as Duel's draw =
   0.5)? The Q4 draw convention in `Q4Rules.md` for rating tables is not defined for the value target.
3. **Arrival estimate** (global 16–19) is not clamped, unreachable is exactly 1.0 and a reachable far seat can also
   read ≥ 1.0 (`(d − 1) · n + order + 1 > 64`, from `d = 17` with 4 alive seats). Clamp, or change the unreachable
   sentinel (e.g. 2.0)? Changing it now costs nothing (no net is trained yet).
4. **Eliminated-seat inputs and outputs.** The value head still outputs a logit for an eliminated relative seat. The
   search should mask it; should the loss do so too (target 0)? `Q4IO.md` §5.2 masks only the misc distance targets.
5. **Threads and batches.** `evaluateQ4Raw` blocks the caller; a search with `T` threads needs `T ≥` batch size to fill
   a batch (as Duel's). `q4tool nnbench` shows the throughput against the batch size (§8).
6. **Allocation per evaluation.** Each result allocates a 3.5 kB `Q4RawNNOutput` (`make_shared`). Negligible next
   to the network at the measured rates, but a search that evaluates 10^5 positions per second may want a pool.
7. **`Q4Board::initHash` and `Q4Symmetry::init`.** `Q4Symmetry::init` is now thread-safe; `Q4Board::initHash` (round 1)
   still uses a plain flag and must be called once before any thread starts (`Q4Board` constructors call it).
8. **TF32.** CUDA FP32 in NHWC mode runs in TF32 on this GPU (§3.2); FP16, which self-play will use, is unaffected.
